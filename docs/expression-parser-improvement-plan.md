# ExpressionParser 保持现有架构的改进与优化方案

> **前置文档**: [expression-parser-code-review.md](expression-parser-code-review.md)（审查报告，bug 编号沿用其第 4 节）
> **本方案回答的问题**: 不复刻经典算法（递归下降 / Shunting-Yard / Pratt），在**保持现有实现思路**——可变 Expression 树 + 字符级状态机 + 就地树旋转优先级 + 工厂注册 + 解释器求值——的前提下，通过修复 bug、机械化优化和适度调整，能否达到缺陷修复与性能提升？
> **结论**: **可行**，但有一个重要前提必须先讲清楚——
>
> ⚠️ **函数调用缺陷是一个"四点修复簇"，单点修复无效**（本方案设计过程中经沙箱副本实证确认，见第 1 节）：审查报告中 Bug #1 的"最小修复"（删一处 push）执行后，所有函数用例从"括号异常"转为 **求值期 NullReferenceException** 或**新的解析异常**。函数功能要真正可用，必须四点协调修复。
>
> **方案性质**: 本文档是方案说明（含收益与风险全面分析），不含实际代码修改。沙箱验证均在临时目录副本上进行，仓库代码零改动。

## 0. 总体思路与边界

### 0.1 三条战线

| 战线 | 性质 | 改动幅度 |
|------|------|----------|
| **A. 缺陷修复簇** | 实证驱动的定点修复（函数四点簇、一元负号、逗号） | 小 diff，触碰解析器核心区 |
| **B. 性能机械化优化** | 不改算法形态的工程优化（类型化数值、分配消除、字典注册） | 中等 diff，机械可验 |
| **C. 架构微调** | 保持范式的内部整理（不变量集中、死代码清理、解耦） | 可选，分步可停 |

### 0.2 借思想、不复刻实现

本方案从经典方法**借用经过验证的设计思想**，但全部以现有机制的形态落地：

| 借来的思想 | 来源 | 在本方案中的落地形态（非复刻） |
|-----------|------|------------------------------|
| 一元负号 = 前缀规则（而非数字符号特判） | 递归下降文法 | 状态机内的一次**单字符前瞻分派**：符号后随 `(` / 字母 → 产出 Negate 节点（第 3 节） |
| 求值用类型化数值而非字符串往返 | 生产级实践（NCalc 等） | `Expression._value: string → double?`，内部表示替换（5.1） |
| 注册表 O(1) 查找 | 工程常识 | `OperatorFactory` 内加字典快路径，保留 `Support()` 虚方法扩展点（5.4） |
| "R" 往返格式保证精度 | .NET 实践 | `ToString("R", InvariantCulture)`（4.2） |

### 0.3 明确不做的事（与经典算法重写的边界）

- ❌ 不引入独立 tokenizer 两阶段（保持单遍字符级状态机）
- ❌ 不用运算符栈/输出栈替换树旋转（保持就地优先级爬升）
- ❌ 不引入 Pratt 绑定力表
- ❌ 不改不可变 AST / 自底向上构建（保持可变树 + Parent 指针）
- ❌ 不引入 Visitor 全套

## 1. 证据升级：函数缺陷是四点修复簇（沙箱实证）

### 1.1 实证方法

将 7 个源文件复制到沙箱目录，**只应用审查报告的"最小修复"**（删除 `ExpressionBuilder.cs:145` 函数路径的孤儿 `bracketStack.Push`），编译运行 11 个用例（方法与完整输出见附录 A）。结果：

| 组 | 用例 | F-1 单独修复后 | 判定 |
|----|------|---------------|------|
| guard | `1+2*3` / `(1+2)*3` / `((3+5)*4)` | 7 / 9 / 32 ✅ | 普通括号路径无损 |
| guard | `-(2+3)` / `1,2` | 1 / 1（Bug #2/#4 原样） | 符合预期 |
| **簇** | `sin(0)`、`sin(1)+2`、`sin(1)*2`、`(sin(1))`、`pow(2,3)` | 解析通过，但 **CalcValue → NullReferenceException** | ❌ 新缺陷显形 |
| **簇** | `2*sin(1)` | **ParserException: "Expect operator but found bracket"** | ❌ 新缺陷显形 |

**6/6 预测命中。** 结论：Bug #1 的单点修复只是把失败从解析期挪到了求值期/另一条解析路径。函数功能需要以下四点协调修复。

### 1.2 缺陷簇全貌（F-1 ~ F-4）

| 编号 | 现象 | 根因（行号基于 `ExpressionBuilder.cs`） | 状态 |
|------|------|------|------|
| **F-1** | 所有函数调用抛 "Unmatched left bracket" | `cs:145` 压栈后 `cs:208 i=argEndIndex` + `continue` 跳过配对 `)`，唯一的弹栈点（`cs:272`）永不执行，末尾校验（`cs:483`）必然触发 | 审查报告 Bug #1，已实证 |
| **F-2** | 函数后随运算符（`sin(1)+2`、`sin(1)*2`）→ 求值 NRE | 链接代码（`cs:153-163`）把 funcExpr 挂为根占位节点的 `Left`，根从此成为**无值无运算符的包装节点**（`_value=null`、`_op=null`）→ `CalcValue()` 走到 `_op.Calc(this)` 空引用。另有一处叠加缺陷：`cs:337-357` 的爬升循环若耗尽到无运算符祖先则跳过重构，随后 `cs:450` 会把 funcExpr 的 Operator **覆盖**为新运算符（当前被 NRE 掩盖） | **本方案规划期新发现，已实证（NRE 部分）** |
| **F-3** | 右操作数位置的函数（`2*sin(1)`）→ 函数名字母被静默丢弃 → 抛 "Expect operator but found bracket" | 函数名累积条件（`cs:131`）只认 `eExpectLeftExpression` 态；`eExpectRightExpression` 态下字母落入数字 FSA → eEnd → 转运算符态重处理 → `Support("s")` 返回 null 被静默跳过 | **本方案规划期新发现，已实证** |
| **F-4** | 括号内单独函数（`(sin(1))`）→ 求值 NRE | 括号持有节点的内容是单个函数调用时同样形成无运算符包装节点（对照：`(2)` 因 `_value="2"` 非空而幸免，`(1+2)` 因获得运算符而幸免——**只有函数子树触发**） | **本方案规划期新发现，已实证** |

> 证据等级说明：F-1 为审查期实证；F-2/F-3/F-4 的**症状**经沙箱实证（1.1 表）；其根因与修法的正确性目前是设计级推演，落地时以 Phase 0 回归套件验证（见第 9 节 R-8）。

## 2. 缺陷修复方案（保持架构）

### 2.1 F-1：删除孤儿压栈

删除 `cs:145` 的 `bracketStack.Push(incomingChar)`。括号匹配已由 `FindMatchingBracket`（`cs:495`）完成校验；参数内部的括号由递归 `ParseToExpr` 自管各自的栈。普通括号路径（`cs:230` 压 / `cs:272` 弹）不动。

**已实证无害**（guard 组 3 用例全绿）。

### 2.2 F-2 + F-4：占位符替换 + 包装节点塌缩（核心修复）

两个动作配合，让函数子树**走进现有旋转机制的标准路径**：

**动作 1 — 占位符替换（治 F-2 顶层形态）**：函数路径的链接段（`cs:152-163`）改为：若当前节点是"新鲜占位符"（默认构造、`_state==eValueOnly`、无运算符无子节点），则**丢弃占位符，funcExpr 直接成为活动节点**（`expr = funcExpr`），而不是挂为 `Left`。效果：

- `sin(0)` → 根就是 funcExpr → `CalcValue` 正常；
- `sin(1)+2` / `sin(1)*2` → funcExpr（eClosed）作为根遇到运算符时，命中**现有的** `Parent==null` 包装分支（`cs:358-363`：newExpr.Left = 整个 eClosed 子树）——即标准旋转路径，无需新逻辑。

**动作 2 — 包装节点塌缩（治 F-4 括号形态 + 兜底 F-2 爬升耗尽）**：在 `Expression.CalcValue()` 增加一个防御分支：

```
_value 为空 且 _op 为空 且 Left != null  →  return Left.CalcValue()   // 透明包装
```

两点依据：① 死代码 `OperatorBracket.Calc()`（`Operator.cs:146-148`）**恰好就是这个语义**（`return expr.Left.CalcValue()`）——作者废弃的设计里早已预留了包装节点语义，本方案只是把该语义复活到正确的位置；② 它同时兜住 F-2 的爬升耗尽叠加缺陷（`cs:337-357` 耗尽到无运算符祖先时应镜像 `cs:358-363` 做包装——建议同时补上这个对称分支或以断言+异常暴露，二选一，见 6.A-2）。

### 2.3 F-3：右操作数位置的函数识别

`cs:131` 的函数名累积条件从

```
currentState == eExpectLeftExpression && Util.IsAlpha(...)
```

扩展为

```
(currentState == eExpectLeftExpression || currentState == eExpectRightExpression) && Util.IsAlpha(...)
```

并在函数路径的链接段区分状态：`eExpectRightExpression` 时 funcExpr 挂为 `expr.Right`（而非 Left）。后续运算符照常走爬升（此时父节点已有运算符，`cs:343` 的 `Priority <= op.Priority` 条件正常命中——设计期追踪：`2*sin(1)+3` → `*(2, +(sin(1),3))` ✓）。未知函数错误路径（`cs:217` "Unknown function"）天然复用。

### 2.4 修复后的语义验收矩阵（Phase 1 回归测试的骨架）

| 用例 | 期望 | 依据 |
|------|------|------|
| `sin(0)` / `pow(2,3)` / `log10(100)` | 0 / 8 / 2 | F-1+F-2 |
| `sin(1+1)` / `sqrt(9+16)` / `cos(3*2)` | sin2 / 5 / cos6 | F-1+F-2（复合参数） |
| `sin(1)+2` / `sin(1)*2` | sin1+2 / sin1×2 | F-2 动作 1 → 标准旋转 |
| `(sin(1))` / `((sin(1)))` | sin1 | F-4 动作 2 |
| `2*sin(1)` / `2*sin(1)+3` | 2sin1 / 2sin1+3 | F-3 |
| `sin(cos(1))` / `sin(pow(2,3))` | 嵌套正确 | 递归 ParseToExpr + 占位符替换在递归内同样生效 |
| `2+s(1)` | ParserException "Unknown function 's'" | 错误路径不回退 |
| guard：`1+2*3` 等全部审查 sanity 组 | 不变 | 保护现有正确路径 |

## 3. 一元负号方案：启用作者预留的 UnaryOperator 槽位

这是本方案中唯一一处"适度调整算法"的地方——**把一元负号从数字 FSA 特判升级为前缀分派**，但实现形态完全长在现有机制上。

### 3.1 分派规则（单字符前瞻，状态机内完成）

```
符号（+/-）已积累（FSA 处于 eHasSign、numericStr 为裸符号）时，看下一个有效字符：
  ├─ 数字 / 小数点 → 维持现状：继续数字 FSA（"-32"、"2*-3" 现有正确路径，零改动）
  └─ '(' 或 字母   → 中止 FSA，产出 Negate 节点，括号/函数成为其操作数
```

前瞻无需新机制：现有循环天然逐字符到达，只是把"符号悬置时遇到 `(`/字母"从当前的静默错绑（Bug #2）改为显式分派。

### 3.2 两个实现选项

| | **选项 B（推荐）：OperatorNegate : UnaryOperator** | **选项 A（快速）：0 − x 技巧** |
|---|---|---|
| 做法 | 新增 `OperatorNegate`（Priority=2，操作数放 Right，复用 FunctionOperator 的"参数即子节点"惯例），`Calc` 返回 `-Right.CalcValue()` | 构造 `OperatorSub`，`Left = new Expression("0")`，负号目标成为 Right |
| 语义纯度 | ✅ 树即语义；`ToString()` 可打印 `-（...）` | ⚠️ ToString 往返会显示 `0-(2+3)`——语义等价但显示失真 |
| 架构契合 | ✅✅ **`UnaryOperator` 空标记类（`Operator.cs:36-38`）正是作者预留而从未启用的槽位**——本方案让它转正 | ✅ 零新类型 |
| 新代码量 | 一个 ~30 行的类 + 分派点 | 仅分派点 |
| 优先级交互 | Priority=2 与 FunctionOperator 同级（"比四则绑定更紧"），经设计期追踪验证与现有旋转兼容：`-(2+3)*3`→-15 ✓、`-(2+3)+10`→5 ✓、`2*-(3)+1`→-5 ✓ | 复用 Sub 的 Priority=0：`-(2+3)*3` → 0-((2+3)*3)=-15 ✓ 同样正确 |

**推荐 B**：代码量差异可忽略，换来树语义干净、ToString 往返不失真、并激活作者自己的设计预留。A 可作为 B 落地前的临时止血。

### 3.3 边界行为（需固化为测试）

- `--(2+3)`：保持现状 **throw**（FSA 的 `allowSign=false` 拦截，`cs:628-643` 路径）——不引入双负号语法；
- `-  (2+3)`（带空白）：空白在 `cs:125` 被跳过，分派不受影响 → -5；
- `-(2)`：单操作数，-2（现状碰巧正确，修复后**必然**正确）。

## 4. 其余正确性加固

### 4.1 Bug #4：函数外逗号 → 显式异常

`cs:317-324` 的静默提前返回改为 `throw new ParserException("Comma is only valid inside function arguments", i, expressionStr)`。逗号在合法输入中只存在于函数参数内，而参数文本在主循环见到之前已被 `SplitFunctionArguments` 抽走——**主循环见到逗号必然非法**。

> ⚠️ 行为变化声明：`1,2` 从"静默返回 1"变为"报错"。这是把静默数据丢失转为显式错误，属正确方向，但 UI 用户若曾依赖此行为（不太可能）需知悉。

附带收益：该提前返回是 `ParseToExpr` 外层循环存在的唯一理由（审查报告 3.5 节），修复后外层循环成为可简化的死代码（见 6.A-4）。

### 4.2 H-2：文化设定三连修（潜在的国际化正确性 bug）

三处独立隐患，一次修齐：

1. `double.Parse/TryParse`（`Operator.cs`、`FunctionOperator.cs` 全部运算符）→ 加 `CultureInfo.InvariantCulture`。当前在小数点为逗号的区域（de-DE/fr-FR）下 `"1.5"` 解析失败或错解析；
2. `ToString()` → `ToString("R", InvariantCulture)`。net48 默认格式不保证 double 往返，深层树求值可能累积精度漂移；"R" 是往返保证格式；
3. `functionName.ToLower()`（`cs:141`）与每个 `FunctionOperator.Support` 内的 `opStr.ToLower()` → `ToLowerInvariant()`。土耳其语区域下 `"SIN".ToLower() → "sın"` ≠ `"sin"`，函数识别将区域性失败；且每次函数名查找触发 **14 次 ToLower 字符串分配**（性能问题一并消除，见 5.4）。

### 4.3 H-1：ExpressionState 枚举 flag 语义修复（规划期新发现）

**证据**（`Expression.cs:9-17`）：

```csharp
eInvalid = 0, eValueOnly = 1,
eLeftValueValid,      // 隐式 = 2 ✓
eRightValueValid,     // 隐式 = 3 ✗ —— 3 不是 2 的幂！
eOperatorValid,       // 隐式 = 4 ✓
eAllValid = eLeftValueValid | eRightValueValid | eOperatorValid,  // = 2|3|4 = 7
```

`eRightValueValid=3` 与 `eValueOnly(1)|eLeftValueValid(2)` 位重叠：`_state |= eRightValueValid` 会**顺手把 eValueOnly 位点亮**，`==` 比较全部不可靠。当前被掩盖仅因热路径检查恰好是 `== eValueOnly` / `IsValid` 复合条件。修复：显式 `= 1, 2, 4, 8` 幂值（`eAllValid = 2|4|8 = 14`）。落地前审计 `ExpressionUnitTest` 是否断言过具体 State 值（见 R-5）。

### 4.4 H-3 / H-4：小加固

- `cs:448` `Debug.Assert(false)` → `throw new ParserException(...)`（Release 下 Assert 是空操作，当前会留下不一致状态）；
- 数字 FSA 的静默 fall-through 分支（`cs:628-651` 区域，如 eHasSign 态遇非法字符返回 `isValid=false` 且状态不变）做一次审计，原则：**任何被消耗的字符必须要么推进状态、要么抛错，禁止第三种"静默忽略"结局**——Bug #4 即此模式的已证实实例。

## 5. 性能优化方案（机械化，不改算法形态）

> 收益倍数为量级估算，Phase 0 建立微基准后以实测校准（见 R-8）。

### 5.1 P-1：`Expression._value` 类型化（收益最大）

**现状**：字符串存值，每层求值 `double.Parse → 算术 → ToString` 往返。n 节点的树求值 = 2n 次字符串操作 + n 次解析。
**改法**：`_value: string → double?`；解析器在**数字词元完成时**解析一次存 double；所有 `Operator.Calc` 直接算术；`ToString` 用 `"R"` 格式还原。
**收益**：求值路径字符串操作归零，估算 **5-20×** 求值加速；精度漂移（4.2-2）与解析文化问题（4.2-1）随之一并消除——一个改动消灭三类问题。
**风险/代价**：触点最广（Expression、18 个运算符、解析器词元路径、ToString、测试断言）；ToString 输出格式可能变化（如 `0.30000000000000004` vs `0.3`），需显式定格式策略并同步更新测试（R-4）。**排在最后做**，前面的回归套件越厚越安全。

### 5.2 P-2：数字词元的分配消除

**现状**：① 逐字符 `numericStr += ch`（每数字 O(k²) 字符串拼接）；② `cs:468` 在 `eExpectRightExpression` 态**每个数字位 new 一个 Expression**（k 位数 = k 次分配 + k 次 Parent 重指，只有最后一个存活）；③ `cs:308` 逐位 `expr.Value = numericStr`。
**改法**：记录数字起始索引，词元结束（FSA 转 eEnd 或串尾）时**一次性**切片、解析、建叶节点；`eExpectRightExpression` 的 Right 赋值同样推迟到词元结束。
**收益**：每数字的分配从 O(k) → O(1)，拼接 O(k²) → O(k)。解析期总分配从 O(字符数+位数) 降至 O(词元数+节点数)。
**风险**：词元结束的冲刷时机必须排在运算符处理之前（`cs:312` 落穿 / `cs:472` `i--` 重处理是现成的冲刷钩子）；`CalcValue`/`IsValid` 均不依赖中间半成品值（已核实：`IsValid` 只看 `_state`，求值不发生在解析中），推迟安全。

### 5.3 P-3：逐字符空白的零分配判断

`cs:125` `string.IsNullOrWhiteSpace(incomingChar.ToString())` **每字符分配一个字符串**只为判空白 → `char.IsWhiteSpace(incomingChar)`。零风险，一行改动。同理 `cs:328` `Support(incomingChar.ToString())` 的 char→string 分配在 5.4 中一并消除。

### 5.4 P-4：OperatorFactory 字典快路径

**现状**：`Support()` 对 18 个运算符线性扫描虚调用；函数名路径更重：`cs:141` 一次 `ToLower()` + 每个 `FunctionOperator.Support` 内**又一次 `ToLower()`** → 单次函数名查找 = 14 次字符串分配。
**改法**：工厂构造函数内建 `Dictionary<string, Operator>`（符号与函数名两套键，OrdinalIgnoreCase 比较即天然大小写不敏感，顺带消灭 4.2-3 的土耳其语隐患）；`Support()` 先查字典、miss 再走线性扫描（保留 `Support()` 虚方法作为外部扩展点，向后兼容）。
**收益**：O(18) 虚调用 + 14 次分配 → O(1) 零分配。

### 5.5 P-5 / P-6：可选项

- **P-5**：函数参数免 Substring——`ParseToExpr` 增加 `(string, start, end)` 重载，`SplitFunctionArguments`/`FindMatchingBracket` 传索引区间。消除每次函数调用的参数串分配。触签名，收益中等，**可选**；
- **P-6**：`CalcValue` 记忆化——解析完成后树不再变动，首次求值后缓存于节点、setter 失效。适合"一次解析多次求值"场景；当前计算器为一次求值，收益小，**可选**。

## 9. 风险与缓解（全面说明）

> 按影响 × 概率排列；每条含缓解措施。

**R-1 函数簇修复触碰旋转/括号核心区（高风险区手术）**
修复 F-2/F-3 恰在审查报告指出的"最难正确推理区域"（`cs:326-455` 旋转 + `cs:367-440` 标志搬运）。可能伤及当前**正确**的 `+-*/()` 路径。
*缓解*：① Phase 0 回归套件先行，含 4 个 guard 用例（沙箱已实证 F-1 单独应用后 guard 全绿——该区域可以在测试护网下安全触碰）；② 修复顺序设计为"让函数子树走进**现有**标准路径"（2.2 的占位符替换/包装塌缩都是复用已有分支），新逻辑面最小化。

**R-2 负号优先级与旋转的交互（设计期已追踪、未实证）**
Negate 的 Priority=2 与三种旋转分支的交互（`-(2+3)*3` / `-(2+3)+10` / `2*-(3)+1`）目前是手工追踪结论。
*缓解*：3.1/3.3 的验收矩阵全部固化为测试；若旋转交互出现反例，回退到选项 A（0−x，复用 Sub 的既有优先级语义，交互面为零新逻辑）。

**R-3 行为变化声明（逗号 throw）**
`1,2` 从静默 1 变为异常（4.1）。方向正确但属用户可见变化。
*缓解*：UI 侧确认无逗号输入路径；发布说明中声明。

**R-4 P-1 类型化的格式涟漪**
ToString 输出与测试断言可能因 "R" 格式变化（`0.3` vs `0.30000000000000004`）。
*缓解*：Phase 3 显式定义格式策略并集中更新断言；此改动排在回归套件最厚的时点。

**R-5 枚举值变更的隐性依赖**
若有代码/测试依赖（错误的）复合值如 `eLeftValueValid|eValueOnly`，H-1 修复会改变其行为。
*缓解*：落地前 grep 全仓 `ExpressionState` 使用点 + 跑全量测试。

**R-6 P-2 冲刷时序**
词元结束冲刷若与运算符处理（`cs:312` 落穿 / `cs:472` `i--`）时序错配，会丢数字或双算。
*缓解*：两个现成钩子位就是冲刷点，单一职责化；专门的边界用例（表达式以数字结尾/运算符结尾/括号结尾三形态）。

**R-7 结构性复杂度降低但不消除（本方案最重要的诚实声明）**
本方案修复全部**已知**缺陷并加固，但**不改变**两个结构性复杂源：可变树的就地旋转 + 括号双重簿记（字符栈 + 节点标志）。F-1 这类"两套簿记脱节"的 bug **类别**仍可能在未来的修改中复发——本次四个 bug 里有三个（F-1/F-2/F-4）源于此机制本身。
*缓解*：① A-2/A-4 把不变量显式化、删死路径，使该区域的推理面收缩；② 设定**重写触发线**（escape hatch）：若后续在此区域再出现 ≥2 个同类回归，应重新评估递归下降重写——那时将有完整回归套件护航，重写风险远低于今天。

**R-8 证据等级与估算不确定**
F-2/F-3/F-4 的根因与修法为设计级推演（症状已实证）；性能倍数为量级估算。
*缓解*：Phase 0 的 characterization 套件 + 微基准就是为把"设计级"升格为"实证级"而设；一切以落地时实测为准。

## 10. 与经典算法的关系定位

**本方案借用的思想**（0.2 节表）：前缀负号分派、类型化求值、O(1) 注册、往返格式——全是"思想搬家"，无一是"实现复刻"。

**刻意不借的**（0.3 节）：tokenizer 两阶段、栈式优先级、绑定力表、不可变 AST——保持现有单遍状态机与树旋转的形。

**何时仍应考虑重写**（承接 R-7）：满足以下任一条件时，递归下降重写的性价比将反超继续修补——
1. 旋转/括号区域再出现 ≥2 个同类回归（触发线）；
2. 需求扩展到现有文法之外（变量绑定、自定义函数、赋值、短路逻辑运算符等）——这些在状态机上的实现成本将远超递归下降；
3. 性能需求达到"编译求值"量级（Flee 式）——那是另一个层级的工程。

在那之前，本方案以 **~4 人天** 的核心投入，换来函数功能从全灭到可用、静默错误类清零、求值 5-20× / 解析 2-4× 的量级提升，且全程有回归套件与 CI 护航——这是"保持现有实现思路"路线下能拿到的完整收益。
